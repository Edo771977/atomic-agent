# Fusion workers

Status: current
Owner: src/tools/fusion/

Fusion delegates bounded task waves to worker turns. Contracts carry deliverables, declared inputs and dependencies. A sibling dependency releases its consumer only after the provider is `ok`, its required matched provides are present and inspectable, and its own deterministic checks and available syntax checker pass. Pathless `other` provides may act as advisory completion tokens: they order successful tasks and retain their cannot-be-checked warning, without proving an artifact exists. Missing or uncheckable matched artifact provides fail the provider; unavailable required checks leave it `needs_orchestrator`. Provider verification is deduplicated only within one release wave; before a later wave reuses the provider, presence, own checks and syntax are revalidated even when intervening workers emitted no file-tool changes. Fresh premerge gates may be reused for the first release. A `no_changes` provider (it wrote nothing) releases its consumers only when every required matched provide is a verifiable artifact that passes that same presence, own-check and syntax verification; its row stays `no_changes` and the consumer's contract still warns about it. Presence alone is not enough: at least one own check or syntax check must actually run in that release and pass (a syntax pass that checked nothing, or no runner, is no evidence). Pathless `other` tokens are no evidence for such a provider. Candidate integration never releases a `no_changes` provider's consumers: promotion requires every row `ok`, so their work could never be delivered. Failed, cancelled, timed-out, queued, step-limited, `needs_orchestrator` and unverified `no_changes` providers hold consumers transitively. This readiness rule applies with `autoReplan` off too: off means no automatic retry; consumers that used to run with a warning are now `not started: dependency blocked`. Cyclic dependencies remain held while independent work can run. Unmatched `requires` remain advisory warnings, as documented by the contract; they establish no sibling dependency and are never described as verified. Presence does not establish semantic compatibility, and call-level integration checks and the final judge still run after the waves. Preserve task status attribution and hand-back based on completed-step progress rather than an independent timer.

## Measured routing (opt-in)

Resumed carried tasks are reported and checked again, but never adapted or appended as new execution samples. Only tasks run in the current call train outcome history; rechecking an old artifact does not establish another provider execution.

The history reader validates task-record structure and keeps a 10,000-record ring while parsing. Dense malformed rows cannot overflow a spread call or build an unbounded record array. Unexpected history failures preserve the current default route.

Routing selects configured provider legs, retaining existing display/pricing labels; it adds no per-request model override. Eligible samples also need a matching opaque SHA256 request-configuration identity, captured at worker dispatch and unchanged at completion. The runtime derives it from provider kind, safe endpoint identity and explicit request model, or a managed main local model whose configured/live IDs match. Credentials, query strings, raw URLs and command arguments are never written to the log. Legacy/unidentified records, automatic model selectors, unknown adapters, subscription CLI argument routing and dynamic external local servers remain insufficient. No provider call discovers identity. This partitions known configuration changes; it does not attest which weights a remote gateway actually served, nor prove model-quality benchmarks.

Cloud identity must match both live configuration and the registry's defensive snapshot of the entry that successfully built the loaded provider. Pending model or endpoint edits and failed replacements remain unidentified until reload succeeds. Managed local identity additionally reads the loaded provider's actual text-client endpoint (including its pinned override) and tracked model ID; a vision-only entry URL cannot establish text identity. It must match the configured main managed endpoint/model. External local servers remain insufficient. A dynamic text client may follow the current main endpoint; a pinned old client cannot inherit a new endpoint's history identity.

`llm.runMode.fusion.measuredRouting: { "enabled": true, "minSamples": 8, "days": 30 }` enables deterministic selection for unpinned tasks using recent outcome history. It is off when absent or disabled. `minSamples` accepts 3–1000 and `days` 1–365. Explicit task models and configured role pins always win. Eligible alternatives are the configured build-role target and the existing orchestrator worker target; CLI targets whose own tools stay on and extra local models prohibited by `mixLocalModels` are excluded. Automatic orchestrator tasks consume the existing per-turn strong-task cap. Request budgets, provider pins, approval scopes and failure breakers still apply; retry families are never automatically rerouted.

[measured-routing.ts](measured-routing.ts) reads the live outcome file plus its two rotations through the existing reader, capped at 5 MiB per file and 10,000 newest retained records. Missing/malformed history falls back to the current route. Selection requires enough first-attempt, non-escalated objective task-check outcomes on both sides, matched exactly by requested task role, provider and model. Privacy-sanitized path aliases are insufficient for exact attribution. Legacy rows, self-reported success, judge-only green, held merges, retries and unverified checks do not establish acceptance. New `acceptance`/`acceptanceScope` fields describe only declared task checks; they do not establish full integration correctness. They are also not independent of the worker: the checks run in the workspace the worker edited, so a worker that weakens or deletes a test, or edits a file the check command reads, earns `checks-passed` there. The outcome row records only check counts, and check specs are free-form commands whose file inputs are not declared, so the log cannot tell such a sample apart; a `checks-passed` row is evidence about the declared checks as the worker left them, not about the original tests. Candidate inner runs must not train this history before final acceptance.

Acceptance rate takes precedence: a gain of at least 10 percentage points can change the route. At equal rates, a target needs at least 20% lower median cost (only when all compared samples have known prices), otherwise at least 20% lower median duration. Missing prices remain unknown, never zero. Candidate order is deterministic, with the current worker winning ties. Latest infrastructure, permission, timeout or cancellation failures keep the default route or exclude an alternative; quality data cannot bypass a blocker. A transient block (timeout, cancellation, an unreachable or overloaded server, any class other than those below) lasts 24 hours from that row (`ROUTING_BLOCK_COOLDOWN_MS`): an excluded alternative is never run again and so never writes a newer row, and without expiry one timeout would exclude it for the whole history window. After the cooldown the leg's verified history counts again; a new blocking row restarts it. A credential or configuration failure (`not-signed-in`, `out-of-credit`, `cli-missing`, `tool-protocol`) does not heal on its own and blocks for the whole history window, until a newer row on the leg replaces it. `details.routing` records the selected provider/model, reason, sample counts, descriptive rates, known costs and exclusions. These observations are neither a benchmark nor a prediction for the current task. They never enter the cached prompt prefix; hermetic fixtures test policy without provider spend.

Routing selects configured provider legs using the existing display/pricing model labels; it does not add per-request model overrides. These labels identify configuration, not independently observed serving-model provenance or model-quality benchmarks. Provider pins retain the existing fallback restrictions.

## Worker lifecycle

`maxWorkers` bounds the entire `fusion.delegate` call across the main worker, role-model and orchestrator pools. Each call owns a FIFO permit queue; independent calls keep independent ceilings. Active legs retain their physical slot, per-provider-pool `cloudWorkers` and strong-model limits. The result's `maxWorkers` is the smaller of the requested width and the sum of those active capacities; `cloudWorkers` is not a new aggregate cap across cloud providers. A call that names no `maxWorkers` is bounded by that sum alone: the unnamed default (one worker on an unpinned local main leg, else `workers`) sizes only the main leg, never cloud role or orchestrator legs. With no `maxWorkers` and no pinned `runMode.fusion.workers`, all slot-affine (local) legs, the main leg and any local role leg (`mixLocalModels`), share one local worker at a time, since they draw on the same GPU; cloud legs still add their own widths beside it. A local main pool with no assigned tasks does not constrain cloud-only role work. The result's slot or cloud-cap note is judged on the main leg's own tasks and width, with or without role legs beside it. A queued task is admitted again against cancellation, turn budgets and failure breakers before its session and task clocks start. Its scheduler wait appears separately as the row's `schedulerQueueWaitMs`, and the call's result adds one line counting the tasks that waited and the longest wait; provider first-token `queueWaitMs` keeps its existing meaning. Permits are released on completion and failure before split expansion or retries acquire their own. A task whose time limit or first-token clock fired but whose turn has not settled gives its permit back after `TASK_PERMIT_RELEASE_GRACE_MS` (5 s), so a turn that ignores its abort cannot starve the call; its row is still reported when the turn ends. An escalation re-run (`escalationReplace`) after such a release first waits for a permit again like any queued task (if the turn is stopped meanwhile, the re-run is not started and the row says so), and the re-run's own time limit or cap arms the same grace.

Verification through `verify.run` requires a throwaway workspace copy. If the copy exceeds its 2 GiB limit or cannot be created, command, service and page runs all fail before starting an executor; there is no in-place fallback. The result carries `errorCode: "workspace-unavailable"`, `isolated: false` and failed, unevaluated checks with the setup reason. Cancellation before execution also starts nothing and cleans up a completed copy. Existing dependency-directory links and user symlinks retain their targets: this copy is not a process sandbox.

`fusion report` retains the JSON `green` / `firstPassGreen` fields as reported task-status counters: `status: "ok"` alone can increment them, even with judge off and no acceptance evidence. Human tables label these as reported green and reported first-pass. Separate `checksPassed`, `checksFailed` and `checksUnverified` counts require consistent `acceptanceScope: "task-checks"`, terminal status, failure and merge flags, with no judge retry or escalation. A later replan attempt can still have check evidence; the measured-routing selector keeps its stricter first-attempt eligibility. Legacy, incomplete and contradictory records remain unverified. These counts describe the declared checks in the worker's workspace: the worker can modify the checks and their inputs, so passing them does not establish semantic correctness or full integration acceptance.

Workers are ephemeral: no durable session row/reflection/trace; no recursive delegation or invisible interactive approval. Provider pins must not fall over to a different billing/model leg. Declared input replacement remains forbidden. A worker's approval-gated call is refused by its session policy. A fan-out's directory covers its writes and ordinary commands there, never a dangerous command (`shell_dangerous`), the agent's own config or secret files (`trust_config`, `state_secret`), mail, passwords or payments: those are refused with `FUSION_WORKER_OPERATOR_ONLY_REFUSED`, and the task comes back `needs_orchestrator` with a note telling the orchestrator to hand the step to the user instead of re-sending it (ATO-1222, ATO-1223). A fan-out whose write scope lies inside the agent's own state directory (`~/.atomic-agent`) is refused before the operator is asked, and the worker brief says an operator-only refusal is reported, not sent back for a re-send (ATO-1267). Concurrency is resolved from the call, task count and serving slot capability, rather than blindly capturing startup state.

A local worker leg has no reasoning-effort parameter, so [worker-runner.ts](worker-runner.ts) turns `workerReasoning` (or its unset default) into the turn's `reasoningBudgetTokens` (`localWorkerReasoningBudgetTokens` in `src/llm/reasoning-budget.ts`); the step applies it to the per-request grammar only, and the forced final step stays unbounded. The levels and default are in the root README's Run modes section. A cloud worker leg gets no bound and needs none for a fallback: every worker turn is pinned to its leg's provider and a pinned request never falls over ([llm-fallback-seam.ts](../../runtime/llm-fallback-seam.ts)), so a cloud worker's step cannot land on a local grammar link. If pins ever fall over, compute the bound where the link is resolved (`prepareForLink`). The step reports on `llm_completed` (`reasoningBoundTokens`) the bound the serving request really carried, which is absent with a plain-instruct profile or a native-tools link; the time-limit hint names the bound only then.

A worker brief ([worker-prompt.ts](worker-prompt.ts)) puts the task, its files, deliverable and contract part, and the rules first, then the quoted original request (at most 6,000 chars on a local leg, 16,000 on a cloud one; a local leg's `### fusion` block and the `fusion.delegate` summary tell the orchestrator to put in `instructions` what a task needs past the 6,000) and a one-line task reminder; a clip of the worker's pinned request cuts inside the quote, never the task. The quote cap does not narrow input-file protection: each worker session carries the whole request (`FusionWorkerMeta.operatorRequest`), and the input guard reads that, not the brief's clipped quote (`workerRequestRecord`). On a local leg the `### fusion` block sizes tasks at one file or function and ~N new lines, N being the worker's completion cap over 25 tokens a line (`workerMaxNewLines`), and a local task writing more than three files (tests, fixtures, snapshots and contract inputs not counted) gets a warning, never a refusal: on the fan-out's approval line, before any worker starts, and on the result (`localTaskSizeWarnings`, `details.sizeWarnings`), the first thing the orchestrator reads after the call.

After a local worker is cut off (time limit, queue wait, hand-back or operator cancel), the next local dispatch first asks the server `GET /health` ([local-leg-health.ts](local-leg-health.ts), ATO-917); a server that does not answer fails the task at once with a restart hint instead of letting it wait out its budget. A server that does answer gets the worker on fresh connections: the process's HTTP pool is swapped for a new one first (`renewTransportPool`, ATO-1357), the part of an agent restart that cleared the field case, while requests already in flight keep their sockets. A worker that still gets no token while `/slots` shows every slot idle is told the request got stuck on the agent's side, not to restart the server.
Worker spend is priced per completion with the prompt-cache discount (`estimateUsageCostUsd`, ATO-918). With `llm.runMode.fusion.turnBudgetUsd` / `turnTimeBudgetMs` set, [turn-budget.ts](turn-budget.ts) caps a fusion turn (ATO-947): reset at the turn's start, checked before a delegation, before each worker starts and on every worker completion; reaching it stops running workers and returns a plain-words instruction to the orchestrator. Unset, none of it runs.

Before the first fan-out on a local worker leg (after the cheap refusals, before the approval prompt), [local-grammar-smoke.ts](local-grammar-smoke.ts) runs one format check: a completion of at most 96 tokens with a 10 s budget, asking for a `reply` call under a worker step's per-request grammar (its thinking decision, reasoning prelude and tool set, the think bound tightened to 16 tokens so it fits) ([grammar-smoke.ts](../../llm/grammar/grammar-smoke.ts)). The completion is grammar-constrained, so this checks that the server takes the workers' grammar and that framing, grammar and parser agree, not the model's skill. Only a definite answer refuses the fan-out — the local server rejected the workers' grammar, or a reply that finished on its own did not parse — with the breaker's tool-protocol words and instruction, noting that blocker on the turn. A timeout, cancel, unreachable server or reply cut at the cap or a stop word has no verdict and dispatches as before. The check is skipped, not queued, while a fan-out this process started is live on that server or its `/slots` shows every slot working. A pass is kept per (server, model, profile, managed daemon launch) for the process, a failure for 10 minutes and a check with no verdict (except a cancel) for 2 minutes; nothing is kept when the model id is unknown. A leg where a worker already finished with a tool call this session is not asked, and that success drops a failure kept for the leg. It runs on the reserved side-call slot (reflection, compaction) when one is reserved, else on slot -1, where the server picks an idle slot and the check clears it; with one slot and the orchestrator on the same server the check is not made. Only the main local server's llama-server legs are probed (the runtime's `fusion-format-check.ts`), never a cloud leg; `llm.runMode.fusion.localFormatCheck: false` turns it off.

[failure-breaker.ts](failure-breaker.ts) stops a fan-out that keeps failing the same way (ATO-1406): one blocker (tool-call protocol mismatch, CLI missing or signed out, out of credit) or `REPEAT_FAILURE_STREAK` identical failures in a row on a leg, and no new task starts there; running workers finish. Trips are kept on the turn's `FusionTurnBudget`, and a later delegation is refused on a leg that hit a blocker, or after the same repeat stopped two rounds. The same state counts rounds and tasks against `maxRoundsPerTurn` / `maxTasksPerTurn` (defaults 6 / 48, `0` off), checked before the fan-out's approval; the approval line names the round and the task count. `model: "orchestrator"` tasks have their own count, `maxOrchestratorTasksPerTurn` (default 4, `DEFAULT_FUSION_MAX_ORCHESTRATOR_TASKS_PER_TURN`; `0` turns the target off and such a task is refused as `orchestrator-target-off`): a call that would pass it is refused whole (`kind: "orchestrator-tasks"`, the message names the cap), per call too when there is no per-turn state, and once it is used no replan fix names that target. Both need the runtime's per-turn `turnBudget`.

[escalation.ts](escalation.ts) escalates a stuck worker (ATO-942): with `escalation: "advisor"`, the first stall or cut first answer asks `ResolvedRunMode.escalation` (a configured provider other than the worker leg) for a hint at most `ADVISOR_MAX_OUTPUT_TOKENS` long, refused when its worst case is over `escalationMaxUsd`, and steers the worker with it. A later stall re-runs the task on that model only with `escalationReplace`. `FusionLiveWorkers` exposes the person's stop / escalate / steer per running worker (ATO-66, ATO-568), keyed by parent session and task id; a person's note rides the shared steering inbox under the worker's ephemeral session id and is read at its next step boundary. `src/http/route-fusion-workers.ts` puts the same three calls on HTTP for the desktop. Escalation spend is added to the turn's cap and reported per row and per fan-out.

[contract-checks.ts](contract-checks.ts) runs the contract's `checks` through `verify.run` (`runChecks`) after the waves. A check's `detail` is the summary's one-line head; a failing check also carries `output`, its stderr/stdout tail with whitespace kept (`CHECK_OUTPUT_CHARS`, 1,500, tail-biased, stderr first), because the head is boilerplate and the assertion is in the tail. The runner is called outside the tool registry, so every text it returns is masked with the shared secret detector (and `knownSecrets`) before any of it is cut, as `compressToolResult` does; every consumer below gets masked text. A task's row keeps one such share however many of its checks failed; the row's block in the delegate result shows it under `check output:` within half the block and a fan-out budget (`FANOUT_CHECK_OUTPUT_CHARS`, 6,000, spent in task order), never on the status table line; the judge's retry brief quotes it under the red check item (`RETRY_OUTPUT_CHARS`).

[syntax-pass.ts](syntax-pass.ts) is the delegate's own syntax pass, so the orchestrator does not spend a strong step on `verify.syntax` after each fan-out: under isolation it runs in each task's workspace before its merge (see below); otherwise after the contract is evaluated (and again on a judge's retried rows), every `ok` row's changed files that are still there (else its declared files) run through `verify.syntax`'s checker (`verifySyntax`, injected as `FusionDelegateDeps.syntaxCheck`), once for the whole fan-out. [syntax-pass.ts](syntax-pass.ts) is the delegate's own syntax pass, so the orchestrator does not spend a strong step on `verify.syntax` after each fan-out: after the contract is evaluated (and again on a judge's retried rows), every `ok` row's changed files that are still there, together with its declared files (a shell command may have written those), run through `verify.syntax`'s checker (`verifySyntax`, injected as `FusionDelegateDeps.syntaxCheck`), once for the whole fan-out. Files outside the session's read scope (working directory, user-named paths, the fan-out's write scope) are not read and are counted as not checked; directories and missing paths are skipped. The table line says `syntax ok (N files)` with what it did not cover (unchecked, outside the scope); a failing file turns the row `failed` with `syntax: N files failed (…)` as its error, the way a failed contract check does, before the judge and the head line see it, and the block carries the errors under `syntax output:` (masked like check output, at most `SYNTAX_OUTPUT_CHARS`, 600). Only syntax demotes: TypeScript runs with `typescript: "parse"`, so only a parse diagnostic (TS1xxx, less the module- and config-dependent codes, `isParseDiagnostic`) fails a file; a type error, a missing module or missing `@types` may predate the worker and is a non-demoting `types: N errors (not demoted)` clause, with the diagnostics under `type errors:` (masked, `TYPE_OUTPUT_CHARS`, 300). `verify.syntax` itself still fails a file on any tsc diagnostic; the other languages' checkers are parse-only already. A checker that throws says so and demotes nothing; with no checker wired no row claims a pass. The pass runs under the delegate's abort signal and a `SYNTAX_PASS_BUDGET_MS` (60 s) budget, either of which kills the checkers (`runChecker` takes a `signal`): at the budget every row reads `syntax: not checked, the pass ran out of its 60 s budget` and none is demoted; a cancelled call gets its rows back untouched. The `### fusion` block tells the orchestrator to re-verify only what contract checks and the syntax pass did not cover.

A row's block opens with a `changed:` line the runtime writes from the worker's own `tool_call_executed` results ([worker-changes.ts](worker-changes.ts)), never from its reply: each path the file tools wrote, edited, patched, moved (a moved directory carries the changed files under it), restored or trashed, relative to the worker's folder (its workspace under isolation, so the path names the merged file), with the lines added and removed (`addedLines` / `removedLines` on the write, edit and patch details; `rewritten` when a replaced file was too large to read), at most `CHANGED_PATHS_SHOWN` (12) paths, then `+N more`. Shell commands are not seen: once one ran (`os.shell.run`, an archive extraction, a skill script, a checkout, a `verify.run` that was not isolated; `UNTRACKED_WRITE_TOOLS`) the line reads `changed (file tools only; shell commands ran):`, so it is not taken as the whole list; the declared-file check and the syntax pass over the declared files cover the rest. A green (`ok`) row whose task declared `files` shows only what `compactGreenReply` keeps of its reply: the first (STATUS) line (`GREEN_REPLY_CHARS`, 200), its ASSUMPTIONS unless they say none, and any line naming a contract deviation ("provided differently", "could not provide"), at most `GREEN_REPLY_KEPT_CHARS` (400) in all, which is what the brief says the orchestrator reads; every other row, and a task with no `files` (its reply is the result), shows the reply whole. The brief asks for a `STATUS / CHANGED / CHECKS RUN → result / ASSUMPTIONS` reply, status first (`WORKER_REPLY_RULE`); the runtime line does not depend on a worker following it.

[worker-self-check.ts](worker-self-check.ts) lets a worker fix its own mistakes with local tokens instead of a round of the orchestrator's. Its brief lists the checks attributed to its task ("Your checks") and says to run them with `verify.run` before replying. When its turn ends with a plain `reply` that would be `ok`, the runner asks what the fan-out will ask: is any declared file absent or a stand-in (`inspectDeclaredFiles`; absence only, since `files` mixes inputs and outputs), and do the task's own checks pass in its workspace (`runChecks`, capped at `SELF_CHECK_MAX_MS`, 120 s, and the worker's remaining time; a run that is cut or cannot run says nothing). On a finding the worker gets ONE notice, the next message of its own conversation (a continuation turn on the same session, policy, signals and clocks), naming the missing paths and each failing check with its output (masked with the registry's secret detector and keys, `WorkerRunnerDeps.knownSecrets`, since the check ran outside the registry), and `SELF_CHECK_GRACE_STEPS` (4) more steps within its step budget; the half-budget hand-back is held during them. It asks only what this task's own state can answer: the self-check runs mid-wave, where under `isolation: "worktree"` the workspace has none of its siblings' files and without it they are still being written, so a check whose spec names a path a concurrent task writes (`concurrentPaths`: that task's `owners` paths and its provides' `in` / `file` names, less this task's own and the `inputs`; concurrent = the same wave or retry, across legs) is not run, and a failure whose output names one gives no finding. Both are left to the post-fan-out run. Skipped for a split proposal, a `NEEDS_INPUT:` question (`readWorkerQuestion`), a refusal, a forced-final-step reply, a worker that replaced an operator input (the orchestrator's to handle), fewer than 2 steps or 10 s left, and for tasks with neither declared files nor own checks. A grace that runs out of its steps keeps its `step_ceiling`: the row is `max_steps`, never upgraded to `ok`. The row notes it, and notes a run cut at the cap (the worker was told nothing). A check the worker's own `verify.run` already passed with the identical spec (keys in any order), in a step after its last step that could change a file (any tool outside `READ_ONLY_TOOLS`, a shell command included), is not run again (`WorkerCheckRuns`). The post-fan-out checks still run as the verdict, so in the success path a worker that ran its checks has them run twice: once by itself, once by the fan-out.

[judge.ts](judge.ts) is the trimmed judge (ATO-944, `judge: "on"`): an acceptance list per task, rendered read-only into its brief (`briefSuffix`); after the waves (under isolation: in the task's workspace before its merge, see below), facts (check outcomes, provide presence, declared files) decide their items and can only be red or green on their own; a fresh-context judge (no transcript) rules on the rest, and only a literal `pass: true` passes. Under isolation it reads the task's unified diff against its workspace's base (`branch-diff.ts`, 3 lines of context, `JUDGE_DIFF_FILE_CHARS` per file): every touched file listed, declared or not, a new file as its head, a declared file left unchanged as its head, all inside `JUDGE_EVIDENCE_CHARS`. Without isolation there is no snapshot of the folder before the wave, so it reads each declared file's first `JUDGE_FILE_CHARS`, or the reply when no file was declared. Each part of the evidence is masked (`maskSecrets`) before it is clipped, so a secret at a cap is never cut in half past the detector; the saved patch in the folder is not masked, so it still applies. A red list re-runs the task once with the findings; the contract is re-evaluated on the retried rows only. Unreadable or impossible judging leaves the task `needs_orchestrator`, never `ok`.

[replan.ts](replan.ts) is automatic replanning (ATO-941, `autoReplan: N`): dependents of a provider that did not close are held regardless of this option (`not started: held for the replan` when on, `dependency blocked` when off), attempts per task are counted per turn in `FusionTurnBudget`, and `details.replan` lists pending and exhausted tasks, each pending one with the `fix` its status calls for (`replanFix`: `max_steps` / `timeout` split it, `no_changes` name the file and the exact edit, two runs still open on a worker leg `model: "orchestrator"`; a family that ran on the orchestrator leg in any round this turn (`FusionTurnBudget.ranOnOrchestrator`) is never steered there again, and still open after two runs it is listed in `failedOnOrchestrator`, to be reported to the person rather than re-sent); a replan may keep a task's id or split it into continuation ids `<id>.<suffix>` (`t3.a`, `t3.b`), which count on the task they continue once it ran this turn and is still open, never on one whose family closed green (`noteRoundOutcomes`: `parse.dates` after a closed `parse` is new work) (`noteRoundAttempts`: one attempt per round per family, so the children share the parent's remaining replans and a split of a split still counts on `t3`); `src/agent/fusion-replan.ts` holds the planner's next step to `fusion.delegate` while any are pending, for at most two steps without a fan-out. A `needs_input` task is a question, not a failure: its `why` carries the question, its fix is to answer it (never the orchestrator's model, never `failedOnOrchestrator`), and when every pending task is `needs_input` the block reads `ANSWER REQUIRED` and the step is not held, so the planner may ask the person.

[role-models.ts](role-models.ts) is models by role and node (ATO-943): `llm.runMode.fusion.roles` maps `plan / build / review / explore / utility` to configured providers (one entry = one model). A task's `model` (must be the worker leg, a role model or `"orchestrator"`, else the call is refused) wins over its `role`, which wins over the worker leg. `model: "orchestrator"` (`ORCHESTRATOR_TASK_MODEL`) is allowed with or without roles: the task runs on the orchestrator leg's provider and model as an ordinary worker turn (worker brief, tool filter, session approval policy, fan-out write scope, read scope, pinned provider), so the orchestrator's own turn still mutates nothing; it is grouped like a role leg and counted against `maxTasksPerTurn` and `maxOrchestratorTasksPerTurn`, but priced toward `turnBudgetUsd` only where `resolveWorkerPricing` knows the leg's price: a subscription CLI leg has none, so there its turns count as $0 and only the count caps hold them (the row says `unpriced: counted against …maxOrchestratorTasksPerTurn`); it never escalates, whatever `escalationProvider` names (the default is that same provider, and any other could only be a weaker model), and its row notes `(the orchestrator's model)`. A Claude CLI orchestrator leg works the same way: the CLI runs with its own tools off and the agent dispatches every call. Its group runs at most `ORCHESTRATOR_TASK_MAX_WIDTH` (2) at a time, under `cloudWorkers`: each is a full turn on the strong leg. A Codex CLI orchestrator leg is refused as this target (`cliToolsStayOn`, reason `orchestrator-target-cli-tools`, and no replan fix names it): Codex runs `-s read-only`, which confines its own shell rather than turning it off, so that shell can read outside the worker's read scope. The same holds for a Codex CLI worker or role leg, which the operator picked and which is unchanged. Each leg's tasks run as their own group (cloud cap for a cloud leg, one at a time on a second local server), priced, counted in the turn's cap, and the row carries `model` / `modelRole`. A second llama-server model is used only with `mixLocalModels: true`; otherwise the task runs on the worker leg and its row says so. `review` is the judge's model when `judgeProvider` is unset; `plan` does not switch the orchestrator. The `### fusion` block lists the role models only when some are configured.
[branch-workspace.ts](branch-workspace.ts) and [branch-merge.ts](branch-merge.ts) are branch isolation (ATO-946, `isolation: "worktree"`, default `"off"`): each run of tasks (a wave, a judge's retry) gets a workspace per task plus an untouched base, all from one snapshot of the working directory. In a git repo a snapshot commit supplies detached `git worktree` metadata, then every tracked path is compared with the original working tree's actual bytes and symlink targets: only a path whose checkout differs (a clean/smudge filter, an eol attribute, a cached-clean index entry) or that was removed is overlaid and charged to the copy limit, while an identical checkout only takes the original's mode and times; each task takes that same frozen base the same way. Git's cached-clean index and clean/smudge filters are not byte authorities. Change detection skips excluded directory names (`build`, `dist`, `target`, …) and ignored directories, except a tracked path or an ancestor of one (`scripts/build/pack.sh`), whose changes are merged and patched like any other. Untracked files and ignored standalone files are copied privately. In direct integration every other ignored directory Git lists (a virtualenv, `.next/`, `dist/`, a cache) is linked to the original exactly like a dependency directory (below), charged nothing: direct mode is not a sandbox, and copying them into the base and every task refused isolation for ordinary repositories; candidate integration copies them privately instead. Elsewhere the workspace is a private folder copy without the original `.git` metadata. Dependency directories named `node_modules`, `target` or `.venv` (`SHARED_DEPENDENCY_DIRECTORIES`) normally get a generated symlink to the original in the base and every task, charged nothing, so a large dependency tree does not refuse isolation. If the host denies a generated directory symlink (Windows without the symlink privilege), a directory junction to the same target is tried; it resolves the same way, so writes through it still reach the original. Only if no link is possible does that entry become a private copy charged to the same cumulative byte limit: the base copies it once and each task links (or junctions) to the base's copy, falling back to a copy of its own only when that link fails too. A refusal caused by such copies says so (`dependency folders could not be linked on this system and copying them exceeds the copy limit (N bytes)`) instead of calling the folder too large, but only when the rest of what was copied (the file that did not fit included) would have fitted without those copies; a large source tree keeps `the folder is too large to copy`. This fallback applies only to runtime-generated links, including links copied from the base; user links retain their targets (except inside a candidate's private dependency copy, below) and are never expanded into copies. When a tracked placeholder (`node_modules/.gitkeep`) keeps the directory itself unignored, Git lists its ignored children instead; each ignored directory under a dependency directory name is linked the same way, while tracked files there are copied. They are never stamped or merged, but in direct integration a write through such a link (a worker's shell or a fan-out-scoped fs write) lands in the original, as with `verify.run`; the same holds for the other linked ignored directories. Candidate integration copies them instead (below). The copy limit (`tools.verify.maxCopyBytes`, default 2 GiB) is cumulative across the base, task copies and frozen ignore-rule files, including tracked byte overlays (only paths whose checkout differs); Git's separate checkout materializations are not charged. If a workspace cannot be created or that copy limit is exceeded, the whole wave is refused before any worker starts, including a retry mixing kept and fresh workspaces; it never falls back to direct writes. [branch-ignore-policy.ts](branch-ignore-policy.ts) freezes ancestor/nested `.gitignore` files and available repository-info/global excludes in a separate private Git evaluator. Newly created ignored directories, and in a folder copy or a candidate existing ones too, stay disposable on both green and failed tasks; a direct merge does not drop their files silently: the files a task added, changed or removed there are listed in `BranchMergeOutcome.ignoredChanges` and in a row note (`not merged: N files under ignored directories (src/generated/api.ts)…`), and a task whose declared `files` or `provides` paths (a `file` name or `in`) lie at or under one of them turns `needs_orchestrator`; ordinary ignored standalone files keep their copy-and-merge behavior. Put deliverables in tracked/unignored paths outside disposable directories. Git is required when a repository or ignore files need classification: if it is unavailable those waves fail closed; plain no-ignore folders can still be copied. Existing user-created symlinks retain their targets, and real worktrees retain Git's common metadata; workspace isolation is not whole-process confinement. The worker's session, brief, write scope, declared inputs and declared-file check all point at its workspace (`RunWorkerTasksOptions.taskWorkspace`). Every directory of a workspace the original also has takes the original directory's permission bits after the copy or checkout (which apply the umask), so a `chmod 775 src` or `700` in the original does not read as a change to the candidate's directory-mode inventory. Copied files keep the original's mtime and atime (and mode), so the declared-file check, which reads an mtime from the worker's start on as a write, reports an idle worker `no_changes` in either mode, candidate integration included; the task manifest is still stamped from the workspace after the copy. After the wave each workspace is merged back in task order, file by file against the base: a file only the task changed is copied in, one the folder also changed is merged with `git merge-file`, anything else is a conflict that leaves the folder's file untouched, saves both sides under `.atomic-agent/fusion-merge/`, turns the row `needs_orchestrator` and returns a `merge-<id>` task in `details.merges` for the planner. A declared input the task removed or cut to under half its lines is refused at merge time. Failed, cancelled, timed-out and queued tasks are not merged. Partial `no_changes`, `needs_orchestrator` and `max_steps` rows remain eligible for merge under the existing integration policy; isolation does not make a wave transactional or verify every partial result. For completed `ok` tasks, the merge gate ([merge-gate.ts](merge-gate.ts)) runs the task's own checks (`check.task`) and the syntax pass on its changed (else declared) files in its workspace and, with the judge on, the judge rules there; a red task is held back (`failed`; one the judge could not verify is `needs_orchestrator`, so autoReplan holds its dependents), the folder untouched, its changes saved by [branch-diff.ts](branch-diff.ts) as `.atomic-agent/fusion-merge/<task>-<hash>.patch` (sanitised id plus a short hash of it) and named in its row's note. With git on the machine the patch is made by git in a throwaway object store (`hash-object --no-filters` of both sides of the touched paths, `diff-tree --binary`), so `git apply` on the folder reproduces the workspace, binary, empty, removed files, symlinks and exec bits included (stamps cover symlinks and modes); without git, the text patch is kept and the rest is copied whole into `<task>-<hash>.files/`, which the note names. The merge folder gets a `.gitignore` of `*`; a task's patch is removed once a later attempt merges green. A judged-red task's workspace is kept (`BranchSet.cleanup(keep)`) and its retry runs in it, so the retry fixes its first attempt against the base it started from and is gated again; kept workspaces are removed after the judge, and in a `finally` around everything after the waves. A gate verdict is reused after the waves unless it went stale (`MergeGateState`): the task's own merge needed `merge-file` (or hit a conflict), a later merge changed one of its files (merged paths plus declared files); a stale task's gated checks and syntax pass run again on the merged folder, and a stale check that fails drops its gate verdict so the judge rules on the folder. Not gated, and run on the merged folder after the waves as before: checks with no owning task, an own check whose spec names a path a concurrent task writes (`concurrentPaths`), and a split's subtasks. Workspaces are removed in a `finally`, on abort and throw too: Node's `rm` deletes the workspace folders first (it removes a generated symlink or junction without following it), then `git worktree prune` forgets them; `git worktree remove --force` runs only for a registration prune left behind whose folder is already gone, so Git never walks a live workspace tree (a Git for Windows recursive delete through a junction could reach the original's dependency directory). The stale-run sweep removes a dead run's worktrees the same way.
[task-tree.ts](task-tree.ts) is the task tree (ATO-940, `taskTree.enabled`, default off; `maxDepth` 2, hard cap 3; `maxNodes` 24). Workers still never delegate: a worker that may split is told how in its brief and steered once at the half-budget hand-back or a cut first answer (`SPLIT_GRACE_STEPS` more steps), and ends its turn with a fenced `split_proposal`. The delegate validates it with `parseDelegateArgs` plus the depth, node and parent-files caps, namespaces ids as `parent/child`, runs the children through the same runner (turn caps, approval scope, child budgets clamped to the parent's), checks their contract and the parent's declared files, and closes the parent row on them. A refused proposal leaves the task `needs_orchestrator`. `details.taskTree` carries the nodes.
[task-profiles.ts](task-profiles.ts) is subagent profiles (ATO-566): a task's `profile` (built-in `explore` / `review` / `research`, or a trusted project's, the user's or a plugin's, see [subagent profiles](../../agent-profiles/README.md)) quotes the profile's instructions into the brief (a `PROFILE` block after the TASK, FILES, DELIVERABLE and contract, before the RULES; on a local leg its instructions are clipped to `LOCAL_PROFILE_PROMPT_CHAR_BUDGET`, 2,000 chars, with a note), narrows the worker's tools to its allowlist (`workerToolFilterFor`, ANDed with the worker policy) and, when the task named no `model` or `role`, sets the role or model from the profile's `model`. A split's children (`task-tree.ts`) run under their parent's profile; a profile a child names itself is dropped. An unknown name refuses the call; `details.profiles` says what was applied, and each profiled row carries `profile` (`{ name, source, tools }`, `tools: "all"` when not narrowed; a non-built-in profile shadowing a built-in's name without `tools` also gets a row note). No task naming a profile, nothing is loaded.
[run-checkpoint.ts](run-checkpoint.ts) and [run-resume.ts](run-resume.ts) let a run survive a restart (ATO-617): one JSON file per run under `<stateDir>/fusion-runs/` (not a table: the session store's schema and turn marks are pinned, and a checkpoint write must never fail a fan-out), written after every finished task (row, spend, side-effect tools as they start) and every wave, deleted on a normal end, kept as `interrupted` when the turn was stopped. A file whose process is gone or stopped is offered (`runtime.fusionRuns`, `/fusion` in the TUI) for 7 days. `fusion.delegate { resume: runId }` replays the checkpoint's own arguments: settled tasks are carried; cancelled, queued and explicitly not-started rows run again, subject to the same side-effect confirmation guard. Spend so far counts toward the turn's cap, and a task whose worker called anything outside the file tools and reads (`toolHasSideEffects`) is not re-run until `confirm: [taskId]`. Checkpoints retain observed changed paths, the shell-coverage flag and a `needs_input` row's `question` (apart from the clipped reply; optional, so older v1 files still load), so resumed artifacts are checked again, including files omitted from `task.files`. JSON input is bounded to 8 MiB and nested task/result fields are validated. Reader-only limits do not reject accepted ids, requests, tool maps or legacy labels within that aggregate budget. New writes bound display titles; arguments, identities and the original request stay exact. Aggregate verification detail is compacted with incomplete coverage rather than making the run unreadable. If exact replay data alone exceeds 8 MiB, or storage is unavailable, the delegate reports checkpointWarning and non-resumability without advertising a run id. The optional v1 metadata keeps old checkpoints readable; an old successful filesystem mutation (including move/trash) without coverage metadata, a new row with untracked shell/archive/skill writes, or a row whose path/notes metadata was clipped becomes `needs_orchestrator` instead of silently passing verification. This records file-tool coverage. Shell writes can escape the observed path list, so a resumed successful row with such writes requires orchestrator verification even when it declared files; the runtime does not claim those names cover every shell output. Desktop has no offer yet.
[outcome-log.ts](outcome-log.ts) is the outcome log: when a fan-out finishes (`FusionDelegateDeps.outcomeLog`), one `"task"` NDJSON record per task that ran (a `not started:` row is left out) goes to `<stateDir>/fusion/outcomes.ndjson`: provider and model (`outcomeLabel`: a value that reads as a local file path keeps only its base name, without a model-file extension), leg (`local` / `cloud` / `orchestrator`), role, status, a failure category from a fixed list (`failureCategory`: the non-`ok` status, else the breaker's blocker class, `syntax`, `checks`, `judge-red`, `not-started` or `error`), the turn's attempt (`FusionTurnBudget.attempts`, counted every round whether or not autoReplan is on, so a manual re-delegation is attempt 2), judge retry, self-check notice and escalations (`WorkerTaskResult.selfCheckNotice` / `escalations`, set by the runner), judge verdict, syntax demotion, steps, time, tokens, cached tokens, cost (`null` unpriced) and merge outcome under isolation (`merged` / `conflict` / `held`). No brief, reply, title, task id, path or error text; the session is `sessionTag`, a 12-hex sha256 prefix. Appends are synchronous whole lines; the file rotates at `OUTCOME_LOG_MAX_BYTES` (5 MB) keeping `OUTCOME_LOG_KEEP` (2), only under the `<log>.lock` O_EXCL file shared by every process ([outcome-log-lock.ts](outcome-log-lock.ts): owner pid, broken when that pid is gone or after 5 s; a writer that cannot take it within 25 ms appends without rotating); a torn last line is skipped by the reader; a failed write is a warning, never the fan-out's error; `llm.runMode.fusion.outcomeLog: false` writes nothing. [turn-receipt.ts](turn-receipt.ts) tallies the turn (`FusionTurnLedger`, opened with the fan-out grant, fed every orchestrator completion through `TurnUsageMeter`'s `onRecord` and every fan-out by the delegate); just before the turn's `turn_finished` the runtime ([runtime-fusion-outcomes.ts](../../runtime/composition/runtime-fusion-outcomes.ts)) emits it as a `fusion_worker` event (role `orchestrator`, task `fusion.turn`) whose summary is the receipt line (strong-side $: the orchestrator's requests, its `model: "orchestrator"` tasks and the judge and escalation calls, one total when all are priced, else each part named, e.g. `unpriced (subscription) + $0.03 judge`; requests, `cache hit X%` of the prompt tokens when cached tokens were reported: `usage.cachedTokens`, or a subscription CLI's `cacheHitTokens` (`completionUsageForTurn`), worker-leg tokens and wall time, tasks ok/failed) and appends a `"turn"` record with the per-step prompt and cached tokens (first `TURN_STEPS_RECORDED`). [outcome-report.ts](outcome-report.ts) aggregates both for `atomic-agent fusion report` and `/fusion report`.

[worker-question.ts](worker-question.ts) is a worker's question (ATO-945): there is no blocking call to the planner (its turn is inside `fusion.delegate`), so a worker that cannot do its task right without an answer ends its own turn with a `NEEDS_INPUT: <question>` line. The task comes back `needs_input` with `question` (at most 300 chars) on its row and a note telling the orchestrator to answer it and send the task again; its declared files are not checked, a failing check does not turn it `failed` (under `isolation: "worktree"` a failing own check or syntax pass holds its changes back as a patch, the row still `needs_input`), the breaker treats it like a finished task, a dependent is warned it did not deliver, and `autoReplan` keeps it open.

## Runtime artifact evidence

A fan-out with artifact or verification evidence exposes `details.artifactManifests[taskId]`, also on each task's `artifactManifest`. The task block's `manifest:` line points to these structured details. Entries use paths relative to the final working folder, actual file kinds/modes, and SHA256 of allowed regular-file bytes or a symlink's link text. Link targets and outside-root ancestor links are not read. No file contents, link text, command arguments, check output or worker claims become manifest evidence. A hash describes the current folder at collection time; it does not upgrade a failed or held-back worker into a successful delivery.

Default inventory comes from runtime-observed file-tool changes (including moved-from/deleted paths), declared files and provide locations. It is explicitly `observed` and incomplete: shell/archive/skill writes can create other outputs, and a declared file list is not a snapshot. Contract/syntax outcomes come only from their runtime runners; missing runners and advisory dependency tokens stay `unknown`. Dependency evidence aggregates all required provides for each provider/requirement pair, matching findings by kind, name and exact search locations. Any missing location blocks the evidence; absent findings remain unknown. Checks that failed are recorded as failed facts, not hidden by the worker's reply. `coverage.complete` describes evidence coverage, not test success; inspect `checks` and `dependencies` as well.

Collection adds no model call. It hashes at most 8 MiB for the entire fan-out, 2 MiB per file, with up to 128 inventory entries per task and a shared 2 s deadline under the turn's abort signal. A manifest is at most 128 KiB of JSON. Missing/unreadable/out-of-scope/changed-during-read files, cancellation and clipped entries are explicit reasons for incomplete coverage. The v1 checkpoint stores this optional, validated field; serialization clipping marks incomplete coverage. Older checkpoints still load. On resume the recorded inventory is recollected before publishing fresh results, including an empty historical manifest: saved snapshot authority is never carried into INNER results. Unidentifiable paths and lost inventory stay explicitly incomplete; persisted hashed entries require a real relative path. Saved hashes are historical evidence, not proof that files stayed unchanged.

`collectArtifactManifest` also accepts an authoritative `snapshot` inventory from runtime snapshot/diff code. Only that inventory may claim complete coverage when all bounds, scope and evidence checks permit it; worker prose cannot select snapshot authority. The collector is independent of candidate execution or promotion.

## Candidate integration

`llm.runMode.fusion.integration: "candidate"` opts into whole-fanout file promotion ([candidate-integration.ts](candidate-integration.ts)). Unset or `"direct"` preserves the existing integration policy above. The original project is approved first; the complete fan-out, its waves and optional per-task `isolation: "worktree"` then run inside one private candidate. Candidate write scopes must stay inside the selected project. Saved project rules still apply; original-path deny/ask rules and declined files map to their candidate copies. Allow rules are not widened by that mapping. Declared inputs and worker refusal policies remain dispatch guards.

Promotion requires every task to close `ok`, all declared provides to be present and inspectable, and at least one explicit `contract.checks` entry. All declared checks run again on the final candidate after all task output and retries, including checks previously passed by an isolated merge gate. Missing runners, skipped checks, cancellation, blocked or partial rows, absent provides and failed checks hold the candidate back. Checks may generate outputs; those final bytes enter the delivery inventory too. This verifies the declared checks, not semantic correctness beyond them. Unmatched external `requires` stay advisory and appear as unknown evidence. The bounded artifact manifest reports incomplete coverage explicitly; the separate complete transaction inventory governs byte delivery. Candidate inner task outcomes are not used as accepted routing history.

The original dirty and untracked state is the merge base. A byte/type/mode inventory, without following symlinks or trusting modification-time caches, must still match before promotion. Concurrent changes hold the entire candidate back; promotion never performs an untested three-way merge. That full inventory is taken once; before each write delivery re-verifies only the target and its ancestor directories (lstat plus bytes, against the merge base overlaid with already-delivered entries), and after the last write it verifies the touched paths once more, so delivery costs the changed bytes rather than one tree scan per path. A concurrent change at a touched path stops delivery and attempts rollback, as does a later write failure or cancellation; an unrelated user edit made while delivery is running is left alone and is not detected. Immediately before each rename, removal, directory creation or directory removal every ancestor directory is lstat-ed again and must still be a real directory with the device and inode that step verified (a parent swapped for a symlink is refused), and the target must keep the identity (device, inode, size, modification/change times, mode) it had when that step hashed it, or still be absent; otherwise it counts as a concurrent change and the user's bytes are kept. The rename or removal itself cannot compare-and-swap, so an edit landing between that last lstat and the call can still be overwritten. Before the first write, promotion creates a journal `.atomic-agent/fusion-merge/<candidate-id>.promotion.json` (requested mode `0600`, written tmp-then-rename with file fsync and best-effort directory sync, including its newly created parents) and a `<candidate-id>.promotion-backup/` folder beside it with requested mode `0700`; each backup file requests mode `0600` whatever the original's mode, which the journal records. A delivered file's temp copy is made writable with requested mode `0600` to open a write-capable handle, then its final mode is restored and both bytes and metadata are fsynced through that retained handle before renaming it, and best-effort directory sync is requested for each change's parent afterwards. Each step is appended as `intent` before its write and marked `applied` after it, with its `path`, `action` (`write`, `delete`, `mkdir`, `rmdir`), `original` and `promoted` entry (`kind`, `mode`, file `sha256`, symlink `linkTarget`; `null` when absent) and, for a modified or deleted file, `backup`: the pre-image bytes, relative to the merge folder; a file or symlink write also names its `temp`, the `.atag-candidate-*` sibling it is staged under before the rename (relative to the project). If the first journal write fails, the backup folder is removed and nothing is delivered. After the final verification, successful delivery writes and file-syncs `state: "committed"` and then deletes both; if that removal fails, the promotion still stands and the report names the leftover journal in `promotionJournal` with a `promotionJournalNote`. A `"committed"` journal means do nothing: the delivery completed and was verified, so just delete the journal and its backup folder. A complete rollback deletes both; a rollback with conflicts keeps them, marks steps `rolled-back`/`rollback-conflict`, sets `state: "rolled-back-with-conflicts"` and names the journal in `CandidateIntegrationReport.promotionJournal`. A journal still in `state: "promoting"` or `"rolling-back"` means the process stopped mid-delivery; nothing resumes it automatically. To restore by hand, walk the steps in reverse: for each `applied` (or `intent`, which may or may not have landed) step, restore `original` (copy `backup` and apply its mode after checking its `sha256`, recreate a symlink from `linkTarget`, recreate a directory with its mode, or remove the path when `original` is `null`), after checking the current bytes are still the `promoted` ones so a later user edit is not lost; delete any step's leftover `temp` file; then delete the journal and its backup folder. The marked private candidate workspace is also retained for comparison. Rollback re-verifies each delivered path individually (a directory it created counts as delivered as soon as it exists, so it is removed while empty even if setting its mode failed), preserves a path edited after delivery and reports any path it cannot restore. This is a guarded file transaction, not atomic visibility across several files or whole-process confinement: existing user symlink targets, Git common metadata, shell commands and external side effects retain their existing boundaries. Directory type/mode replacements that cannot be safely delivered are refused for review, and so is deleting a directory that still holds ignored or disposable entries in the original (they are never removed): the reason lists them before anything is written.

Permission and durability limits: the requested `0600` file and `0700` directory modes provide owner-only POSIX permissions. On Windows, `chmod` changes the read-only attribute rather than installing owner-only ACLs; journal and backup access depends on inherited ACLs. File fsync tolerates `EINVAL`, `ENOTSUP` and `EOPNOTSUPP` from filesystems that cannot flush, so those hosts do not get the corresponding durability guarantee; other errors, including `EPERM`, reject the operation. Directory sync is best effort: it is skipped entirely on Windows, and errors on other platforms are ignored. Persistence of the journal names, promoted renames and directory entries across power loss therefore depends on the host filesystem and directory-sync support.

Private workspace copies retain the existing cumulative limit per branch set (`tools.verify.maxCopyBytes`, default 2 GiB, the same setting that bounds `verify.run`'s copy; it also bounds candidate inventories and hashes), charging actual base/task/ignore-rule copies but not Git's separate checkout materializations. Nothing may reach the original before promotion, so the candidate does not link the shared dependency directories (`node_modules`, `target`, `.venv`) to the original: it gets one private copy of them (`privateDependencyDirectories`), charged to the copy limit; the candidate's base normally links (symlink, else junction), since nobody writes to it; when neither is possible it holds an empty placeholder instead of a second copy, so the dependency tree is copied from the original exactly once. A dependency tree too large for the limit therefore refuses candidate staging; the error names the same reason as an isolation refusal (`candidate workspace unavailable: the candidate's private copy of the dependency folders exceeds the copy limit (N bytes)` when only that copy overflows, else `… the folder is too large to copy`). A user link inside that copy whose absolute target lies inside the working directory (npm workspaces on Windows, pnpm: `node_modules/@s/pkg` → `<project>/packages/pkg`) is pointed at the same place inside the candidate, so a write through it stays private. In a monorepo subdirectory (working directory `packages/app`) the candidate's worktree holds the whole repository's tracked files, so a target elsewhere in the repository (`<top>/packages/lib`) is pointed at the same place in that worktree; when that place is untracked or ignored and so absent there, staging is refused. A folder-copy candidate holds only the working directory, so a dependency link into the repository outside it refuses staging (`the dependency link node_modules/lib points into the repository outside the working directory …`) instead of leaving a write path to the original. A relative target that resolves inside the working directory (from the original link's folder) is kept relative; one leaving it is recreated as its absolute original target, so it neither dangles nor resolves to an unrelated folder beside the copy, and then follows the rules above (this also applies to any dependency link copied because no directory link was possible). Targets outside the repository (without one, outside the working directory) are kept as they are (a write through them is not isolated). Where symlinks are denied, a user link to a directory under a dependency directory is recreated as a junction to the same resolved path; any other user link that cannot be recreated fails workspace setup with a reason naming it. Nested task isolation creates its own branch sets from the candidate, so its task workspaces link to the candidate's copy, never to the original; a worker write there is discarded with a rejected candidate and is never promoted (the folders are not inventoried). Ignored directories remain private, disposable inputs/caches. Unlike worktree merging, candidate promotion also keeps ignored standalone files (`.env`, logs) private: they are copied for checks but excluded from both inventories, so a worker's edit or deletion of them is never promoted. They are classified with the same frozen rules as directories, so a dir-only pattern (`out/`) also keeps an untracked file named `out` private. Work the ignore rules would silently lose is refused rather than dropped: a declared `provides` path (a `file` name or any `in`) at or under an ignored or disposable path rejects the candidate, as does a deleted tracked file whose bytes reappear in a new ignored standalone file (`notes.md` renamed to `notes.log`). Ignored directories are stamped at their top level only, never walked, so a rename into an existing ignored directory is not matched; every new or resized ignored path is listed in `CandidateIntegrationReport.ignoredChanges` and in the tool result's note. A candidate change under the project's agent state folder `.atomic-agent/` (approval rules and other operator-owned state; the root merge folder excepted), or under a nested one at any depth (`pkg/.atomic-agent/`, which a session working in `pkg/` would load), rejects the whole candidate with a reason naming the paths. The folder name is matched conservatively on every platform, in every path component, case-insensitively and with Win32 trailing dots, spaces and `:stream` suffixes dropped, so `.ATOMIC-AGENT/` or `.atomic-agent./` is refused too; an ignored `.atomic-agent/` is simply never promoted. The candidate inventory never applies ignore rules or the dependency/build folder names (`node_modules`, `build`, `dist`, `target`, `.venv`) to a path the snapshot tracks: a tracked `scripts/build/pack.sh` is copied, checked and promoted like any other file. Untracked folders with those names stay disposable (a folder-copy candidate has no tracked paths, so there they are always disposable: outside Git, and also inside a repository that falls back to a folder copy because Git cannot snapshot it, such as one with no commit yet or a merge in progress). Candidate setup is bounded to 120 seconds; each streamed inventory is bounded to the copy limit (2 GiB by default), 100,000 entries and 30 seconds, and promotion has a 120-second deadline. Caller/turn cancellation remains active; declared checks retain their runner's limits. A limit or unreadable input fails closed.

Candidate mode is explicitly non-resumable: it creates no ordinary run checkpoint or run ID and refuses `resume`, so carried green rows cannot be replayed onto a fresh candidate. Gracefully rejected/interrupted changes are retained as the existing binary-capable patch under `.atomic-agent/fusion-merge/`; held inner-task patches are copied there too. Patch/recovery metadata may be written there even when project outputs are rejected. If bounded patch creation fails, the result names the private recovery workspace and cleanup retains it. A recovery ownership marker prevents stale sweeping from deleting it; after inspection/recovery, remove the retained workspace manually (and its Git worktree registration when applicable). A hard process stop cannot produce a final patch: its marked private workspace remains for manual recovery and is never advertised as a resumable run. Successful and fully patched rejected runs remove their temporary workspaces normally.

Candidate inputs inside the project use their declared relative suffix for both worker dispatch and final promotion guards. Absolute declarations retain the same protected original identity; literal braces or brackets in a generated workspace prefix cannot turn them into advisory globs. Genuine glob suffixes retain their advisory behavior. Setup tree stamps and ignore queries carry the setup/caller signal throughout traversal. Recovery tree scans and patch commands share an independent 30-second signal so an already-cancelled turn can still save its patch; expiration retains the marked workspace for manual recovery.
