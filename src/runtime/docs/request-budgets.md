# Fusion completion request budgets

Status: current
Owner: src/runtime/

`llm.runMode.fusion.turnBudgetUsd` shares one admission ledger across a parent turn's planning completions, bound workers, judge and escalation calls. [Turn state](../../tools/fusion/turn-budget.ts) separates held request reservations, settled request charges and carried/external spend. Existing worker usage callbacks keep their display totals; runtime-owned callbacks identify already-accounted requests so the ledger does not charge them twice. Resumed checkpoint spend remains a separate additive charge. Worker ownership is installed and cleared with the worker's approval policy, including failures and escalation replacements; a worker bound to an older parent turn cannot spend from a newer one.

[The link attempt](../llm-link-attempt.ts) creates a [request scope](../request-budget.ts) after preparing the prompt for the provider actually serving the attempt. OpenAI-compatible HTTP invokes that scope immediately before **each physical send**, including internal retries, schema/temperature repairs and fallback attempts. The hook sees the converted messages, tools and model parameters that will be serialized. An override cannot raise the output ceiling after admission: the hook clamps the final output fields to the minimum explicit ceiling: the request's `maxTokens`/`maxOutputTokens`, the provider entry's `maxOutputTokens`, or a `max_tokens`/`max_completion_tokens` field already in the final body. The model context window is never used as an output ceiling (providers reject a window-sized limit, and reserving one would hold dollars per request). It clamps whichever of `max_tokens`/`max_completion_tokens` the body already uses; when the body has neither it writes the wire model's profile field (`max_completion_tokens` for OpenAI reasoning models), never both. No cap preserves the previous request shape and retry behavior.

The scope's `mode` says how a USD cap is enforced. `hard`: an explicit ceiling exists and pricing is verified; the bound above is reserved and the ceiling written. `soft`: pricing is verified but no explicit ceiling exists (the default for preset, wizard and `fusion setup` entries, which write no `maxOutputTokens`); the body is left unchanged and the send reserves an assumed reply of `SOFT_OUTPUT_RESERVE_TOKENS` (8192) tokens, or the verified context window if smaller. Settlement charges real usage, so a soft cap can be exceeded by at most one request's output beyond the assumed amount. `meter`: a paid provider without verified pricing, or an adapter without physical-send support; nothing is reserved ahead of time and the reply's reported cost (or, with verified pricing, its usage estimate) is charged afterwards, so the cap stops the next request rather than this one. `unbilled`: explicit local runners, subscription plans and unpriced loopback/LAN servers. Pricing that comes only from the bundled models.dev snapshot (model source `snapshot`, ATO-647) is never verified pricing for admission ([`verifiedAdmissionPricing`](../link-spend-billing.ts)): such a link stays in `meter` mode under a turn cap or daily limit (no reservation, no clamping, no provider-side-input or `service_tier` refusal), while settlement and the cost readout still estimate its spend from the snapshot rates when the reply reports no cost (cost source `snapshot`). The snapshot is a dated community list that can be stale: the committed one was taken on 2026-11-12 (`MODELS_DEV_SNAPSHOT_DATE`, refreshed by `npm run models:snapshot`), and `/usage` names that date beside any cost estimated from it. Configure `userModels[].pricing` to make a cap hard. For `soft` and `meter` the scope exposes a one-line `hint` (set `maxOutputTokens`, or configure pricing) and a `hintKey` (session and provider); the scope itself does not log, so a caller that surfaces the hint should do so once per key. Behavior change: earlier builds refused these sends ("needs a verified output ceiling", "cannot verify pricing", "cannot authorize physical requests"), which failed every fusion request of a default setup.

Reservation assumes no prompt-cache discount. It estimates input as one token per three serialized UTF-8 bytes of the final body plus a 1024-token framing allowance (a 3-byte CJK character counts as one token), not by the model context window, which would reserve a full window for every short request. The estimate is a planning figure rather than a strict bound; settlement charges real usage. When the final body lets the provider add input of its own (OpenRouter `plugins` or a `:online` model id, OpenAI `web_search_options`, or a `tools` entry whose type is not `function`), the input bound is the larger of that byte bound and the verified model context window; without a verified window such a request is refused. Per-result search fees are external-tool charges this estimate does not cover. Input is priced at the input rate; the cache-write premium is added only when the final body places explicit `cache_control` breakpoints (settlement prices reported cache reads and writes). When the full bound does not fit the remaining allowance, an explicit ceiling is clamped to the largest output the allowance covers, never below 1024 tokens (a ceiling already at or below 1024 is not clamped), and the clamped value is the one written to the body; a soft bound shrinks its assumed reply the same way. If even that does not fit, the request is refused. Price modifiers in the final body are part of the bound. A model's optional `pricing.longContext` (`thresholdTokens`, `input`, `output`, optional `cacheRead`/`cacheWrite`; an omitted cache rate keeps the base model's ratio to its input, e.g. `long.input × base.cacheWrite / base.input`, and is the long input rate when the base declares none) applies when the input bound exceeds the threshold, so a body whose bound crosses it reserves at the higher of the base and long-context rates; [usage pricing](../../llm/provider/usage-cost.ts) bills a reported prompt strictly larger than the threshold at the long-context rates. The threshold is per completion: a fusion worker prices each unbilled long-context step on its own as it arrives, and a summed usage (a worker's steps, a split task's rows) is priced at the base rates, so a task's recorded spend agrees with the per-call settlements. Tier names match without regard to case. A `service_tier` other than absent/`null`/`default`/`auto`/`standard`/`standard_only`/`flex` (for example OpenAI `priority`, set through `extraBody` or model `params`) is refused under a USD cap unless `pricing.serviceTierMultipliers` declares that tier; the base rates bound those listed tiers from above (`flex` is cheaper, `standard_only` is Anthropic's standard tier), so they need no multiplier. Behavior change: earlier builds refused `flex`, `standard_only` and any differently-cased name (`"Default"`) under a USD cap, and matched multiplier keys case-sensitively; a declared multiplier still wins over the base-rate default; a declared multiplier scales both the reservation and the usage-priced settlement (a reported cost still wins unchanged). Settlement uses the tier the response says served the request (the top-level `service_tier` of an OpenAI-compatible response or stream chunk, carried as `usage.serviceTier`): OpenAI serves an `auto` or absent tier at the project's default, which can be priority. A served tier with a declared multiplier settles at it, a base-bounded tier at the base rates, and a served tier with no known price settles conservatively at the whole reserved bound (counted as conservative spend); a response that names no tier settles at the requested tier's multiplier. The config parser rejects non-finite or negative rates and multipliers and a non-positive threshold. It reserves the complete (possibly clamped) output ceiling, including reasoning counted by the provider in its output token limit, and accounts for multiple requested completions. An inference override that bypasses physical-send authorization refuses the request before sending; unknown paid pricing and a missing output ceiling fall back to `meter` and `soft` as described above. Explicit local runners and subscription CLI plans remain unpriced; their existing step/request/token restrictions still apply. This policy covers the runtime's text completions, not separate embedding, image, video or external-tool bills. Embedders that call providers outside the runtime seam must wire equivalent admission; the standalone delegate's legacy usage callbacks only observe completed spend.

On completion, reported cost wins, otherwise reported usage is priced normally. Unused held allowance is released. Definite pre-generation rejection statuses (400/401/402/403/404/405/413/415/422/429) and the 529 overload answer, which a provider returns instead of generating and does not bill, release the hold. A 503 is not released: gateways and proxies (Envoy/Istio "upstream reset before headers", Heroku H12) return it after the body was delivered and generation was billed. A send that fails before any connection exists (`ECONNREFUSED`, `ENOTFOUND`, `EAI_AGAIN`, `ENETUNREACH`, `EHOSTUNREACH`, `EADDRNOTAVAIL`, reported through the optional `onSendFailed` hook) also releases it, so a retry or the surfaced connection error is not replaced by a budget refusal. An ambiguous dispatch failure (a reset, timeout, TLS/socket error or any other transport errno, which can follow a delivered body), 408, 500/502/503/504 and other 5xx, cancellation or abandoned stream without final usage settles the conservative upper bound and releases the hold; a retry needs a new reservation. A setup failure before sending has no charged reservation. These are admission estimates under configured price and provider token-limit assumptions; they do not guarantee a vendor invoice, which can include different prices, provider-side routing or unreported charges.

The capped receipt's `spentUsd` is the accounted amount; its optional `conservativeUsd` identifies the part settled without final usage. That amount may overstate the eventual bill. A parent turn deactivates its request policy at `turn_finished`, so subsequent background work does not inherit a completed turn's deadline or allowance.

OpenAI adapters preserve incomplete token-report provenance even when display counters normalize missing values to zero. Missing or partial unary/SSE usage settles the reserved bound; explicitly reported zero token counts or zero billed cost remain trustworthy zero charges.

`llama-server` and `subscription-cli` kinds are unpriced by contract. Any other kind on a loopback or private-network URL (`isLocalServerUrl`: Ollama, LM Studio, vLLM) is unpriced too while its model has no verified pricing ([link billing](../link-spend-billing.ts)); once the operator prices it, it is treated as a forwarding gateway to a paid service (LiteLLM, a team proxy) and is counted and capped like any paid link. Behavior change: earlier builds treated every non-runner kind on such a URL as paid, so an unpriced Ollama was refused at the daily limit (and `onDailyLimit: "local"` could not land on it) and added an unpriced call to the day for every reply. Any reported dollar cost is still charged, even from those kinds; a contradictory bill cannot disappear from the ledger.

The daily spend limit (`llm.costTracking.dailyLimitUsd`, ATO-649) is a second ledger in the same scope ([daily ledger](../daily-spend-budget.ts)), so the day is counted and capped by the rules above rather than after the fact. A scope exists for every billed link whenever the runtime keeps a day total, with or without a turn budget; unbilled links (`llama-server`, `subscription-cli`, an unpriced loopback/LAN server) never reach the day. With a ceiling set and verified pricing on a link that authorizes physical sends, each send holds the same upper bound against today's allowance, which is the persisted total plus this process's open holds, so parallel sends cannot all pass on an allowance that covers one. With a daily limit alone (no turn USD cap) the ceiling is the reply the provider will actually send: the final body's `max_tokens`/`max_completion_tokens` (after `extraBody` and model params), else the provider's own rule (the request's cap, else the entry's `maxOutputTokens`), not the minimum across them, so a truncation step-up or a larger `extraBody` cap stays on the wire. The bound is clamped to fit the tighter of the two allowances only when the full bound does not fit, and the scope's `hint` then names the clamped size and what is left. A send that cannot fit even the smallest clamped reply is refused with the daily limit error, worded "This request could exceed the remaining daily allowance ($X left of $Y)" while today's total is still under the ceiling. Holds are released on the same rejections and settled in `finish` with the same amount as the turn ledger: reported cost, else the usage estimate at the served tier's multiplier, else the whole hold, so a retried 5xx is charged and an `ECONNREFUSED` is not. One exception keeps money never spent off the day: a send abandoned after it left (a cancel or the turn deadline, with no reply) or a reply with no usage block is counted on the day as a priced call at the send's input bound plus the output known to have arrived (streamed or returned text, at three bytes per token), never more than its hold; the turn ledger still charges the whole hold. A link without verified pricing, or without physical-send support, is metered as in `meter` mode: nothing is held, the send is not refused below the ceiling, the scope carries a `daily spend limit:` hint, and the reply's reported cost (or estimate) is added afterwards; a reply with neither counts as one unpriced call. Without a ceiling the day is metered the same way. The fallback seam's per-attempt hook still refuses early once the persisted total is at or over the ceiling. Fusion escalation and judge calls go straight to their provider, past the seam, so their composition wiring (`escalationComplete` in [the tool catalog](../composition/runtime-tool-catalog.ts)) runs the same early refusal and gives their scope the daily ledger, with or without a turn budget. The settled amount is the only write to the day total, so a call is never counted twice. The hold is per process: another process sharing the state directory sees only settled spend (there is no cross-process lock), so two processes can together overshoot by their in-flight holds.

Foreground compaction, smart approval and query rewriting pass an explicit `budgetOwnerSessionId` separate from their `compaction:`, `risk:` or `rewriter:` routing/breaker partition. The seam uses that owner only for active-turn money and deadline admission; it never infers ownership by stripping a prefix. Background rolling compaction explicitly opts out, and post-turn reflection, naming and consolidation remain independent background work rather than inheriting a completed turn's policy.

HTTP error diagnostics retain the combined deadline/cancellation signal after response headers arrive. Their body reads are limited to 64 KiB, cancel the reader on abort or clipping, and also retain the provider request timeout; a stalled non-2xx body cannot keep a capped request alive past its deadline. When only the provider request timeout fires during that read, the received status stays authoritative: the error keeps its status with `timedOut` false and says the body read timed out, so a 401 is still a credential rejection rather than a slow provider. Caller cancellation and the turn deadline still propagate as cancellation. A 5xx without final usage still carries its conservative dispatch charge.

`turnTimeBudgetMs` also applies to ordinary unary/stream planning calls before and after fan-outs. Each serving request combines the remaining turn deadline with its caller's signal and clears its timer on completion, error or stream abandonment. The fan-out retains its shared deadline through post-wave checks, syntax validation and judging, then reports the final settled spend and elapsed time. Host checks and providers must honor cancellation; the runtime cannot forcibly stop arbitrary code that ignores its signal.
