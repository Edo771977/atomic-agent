# CLI frontend

Status: current
Owner: src/cli/

Owns command parsing and terminal entry points. User turns enter runtime.runTurn; preserve exit semantics, state-dir selection and separation from release scripts.

Entry point: [index.ts](index.ts). Read the root instruction route and the underlying domain instructions before cross-domain changes.

Skill list/show/enable/disable accept `--workspace <dir>` for cloud project scope; `skill project on|off --workspace <dir>` controls all project sources. Without the flag enable/disable remain global. See [cloud skill controls](../skills/docs/cloud-workspace.md).

`run` reads stdin through one line queue ([stdin-line-queue.ts](stdin-line-queue.ts)): every line is kept in arrival order, a line written while a turn runs becomes the next message, and an approval prompt takes its answer from the same queue. A driver can pipe the task, a `y` and the next message at once. The prompt takes only a line shaped like an answer (`y`, `yes`, `n`, `no`, `s`, `a`, or an empty line); any other line denies and stays queued as the next message, so piping "task" and "continue" without an answer loses nothing. EOF before an answer denies, and a prompt that fails denies without stopping later input (ATO-781, ATO-802). Because a piped multi-line prompt still runs one turn per line, the first time a second piped line becomes its own turn `run` prints a one-line notice to stderr; a terminal session gets no notice (ATO-910).

`config get --with-sha256` prints `{"sha256": "<hex>", "config": {...}}`: the normalised config and the lowercase sha256 of the raw `config.json` bytes it was parsed from, from one read (the empty-string hash when the file is missing). `config set - --expect-sha256 <hex>` writes the stdin payload only while the file still hashes to `<hex>`; otherwise it writes nothing, prints exactly `config changed since it was read` to stderr and exits 3. Without the flag `set -` is unchanged. This is the compare-and-swap the desktop uses since it shares the terminal agent's state dir (ATO-416); see [config-sha256.ts](config-sha256.ts).

On a Windows console, startup switches the code page to UTF-8 (65001) so non-ASCII text and the output of console programs the agent runs are not garbled, and restores the original page on exit. It skips a non-TTY stdout (the desktop app reads through pipes), a console already on UTF-8, and macOS and Linux; a failing `chcp` never stops startup. See [windows-console-utf8.ts](windows-console-utf8.ts) (ATO-221).

`doctor [--fix] [--undo] [--json]` (ATO-577) runs a registry of checks ([doctor-checks.ts](doctor-checks.ts)): config.json parses and passes the schema, it is readable by its owner only, and every enabled stdio MCP server's command is installed; a session pin file (`tasks.sqlite`, `webhook-sessions.json`) that exists but cannot be read is a `session-pins` warning with its fix, since retention skips its prune every start until it reads. A check may offer a bounded fix: an unknown `llm.activeTextProvider` becomes the first configured provider (another schema error in the file stays a reported failure), a missing MCP command turns that server off, a loose file mode becomes 600. Broken JSON and other schema errors are reported, never guessed at. `--fix` copies config.json to `<stateDir>/doctor-backups/config-<time>.json` before it edits the tree; `--undo` restores the newest copy and removes it. The state dir comes from `ATOMIC_AGENT_STATE_DIR` without loading the config, so the command runs when the config is the broken thing. Exit 1 while any check fails. Once the config is valid it also checks the local engine (installed, model on disk, enough memory, server running or its port free; external mode: the server answers) or, when a cloud provider is active, its key with one test token ([doctor-engine-checks.ts](doctor-engine-checks.ts)); these say the command that fixes them.

`data backup|restore|move|reset|path` (ATO-579, [data-command.ts](data-command.ts), [data-archive.ts](data-archive.ts)) acts on the state dir the terminal and the desktop share. `backup <file.tar.gz>` writes an owner-only archive with a manifest; each `*.sqlite` goes in as a snapshot through SQLite's backup API, and `models/` (unless `--with-models`), `browser-profile/` (cookies), WAL/SHM, locks and runtime records stay out. `restore <file> --yes` unpacks into a sibling folder, refuses an archive without the manifest, carries this machine's `models/` over when the backup has none, then swaps folders and keeps the old one as `<stateDir>.before-restore-<time>`. `move <dir>` moves the folder (copy and remove across disks) and leaves a symlink (a junction on Windows) at the old path, so both apps keep finding it. `reset --keep-models --yes` moves everything but `models/` to `<stateDir>.reset-<time>`. Nothing is deleted; close every Atomic Agent first.

`overnight "<task>" [--budget <usd>] [--hours <h>] [--dir <path>] [--notify telegram] [--detach] [--no-approval]` (ATO-1113, [overnight-command.ts](overnight-command.ts)) creates one durable one-shot task (origin `cli`, one attempt) with the task's `maxCostUsd` and `maxDurationMs` (ATO-1108) and runs it. No `--budget` leaves the cap to `agent.task.maxCostUsd`; no `--hours` means 8. `--dir` becomes the runtime's working dir, so the run's session and every tool work there. Foreground prints one line per step to stderr ([overnight-progress.ts](overnight-progress.ts)) and a summary to stdout. Exit 0 when the agent finished on its own; 2 when a limit ended the run (the row is `completed` with a `stopCause`, or `blocked` with `budget_spent:` / `time_spent:`), and the summary then says `overnight stopped (<cause>)`; 1 when it failed or was cancelled (ATO-1323). An approval request is denied and counted, since nobody answers it; `--no-approval` boots at the top level. `--detach` re-runs the same command as a detached child (cwd = `--dir`, output to `<stateDir>/logs/overnight-<id>.log`) under a task id it prints first. A `task cancel` from another terminal is seen within 5 s and aborts the turn. The task carries `agent.task.maxSteps` as its step ceiling, so the per-leg `agent.maxSteps` does not end the run. Ctrl+C (SIGINT) cancels the task; SIGTERM and SIGHUP (shutdown, logout) stop the run the way a runtime shutdown does and leave the task pending to resume. Step lines count what the task spent before this run toward the cap.

`fusion report [--days N] [--model X] [--json]` ([fusion-command.ts](fusion-command.ts)) prints the fusion outcome log aggregated per worker model and orchestrator provider (format and fields: [fusion README](../tools/fusion/README.md)); `/fusion report` in the TUI prints the same text. Exit 0, 1 when the report cannot be produced, 2 on a usage error; `--model` matches a model or provider id case-insensitively.

`models recommend --role worker [--json]` ([models-recommend.ts](models-recommend.ts)) names the model for fusion's workers instead of the three tiers: among the models this machine carries, by catalog fusion-worker rating (`good` > `ok` > unrated > `poor`), then room for `localModels.managed.parallel` worker slots, then rank, and prints why. `--json` keeps the default fields and adds `role` and `worker` (`{model, rating, ratingNote, slots, slotsWanted, needGb, why}`, `null` when nothing fits). Without `--role` (or `--role default`) the output is unchanged; another value exits 2.

## Fusion setup

`setup fusion [--yes] [--dry-run] [--judge] [--isolation] [--orchestrator <id>] [--budget <usd>]` ([setup-command.ts](setup-command.ts)) switches to Fusion in one step. [setup-fusion-detect.ts](setup-fusion-detect.ts) reads config.json without creating it (an invalid file is named with "Fix or move <path>", exit 1), loads `.env`, asks `providers status`' check about Claude Code (no turn), and lists models on disk; an external llama-server gets a 1.5 s `/health` probe. The pure [planner](../llm/run-mode/fusion-setup-plan.ts) ranks the orchestrators that can answer: the stored fusion orchestrator unless it is definitely not ready (an inconclusive check, such as the CLI check timing out, keeps it with a warning; a replaced one is named with the reason), then the active text provider when it is a cloud one, then a signed-in subscription CLI (a configured entry, else a new keyless `claude-cli` entry), then other keyed cloud providers with Best/Balanced [tier](../llm/provider/presets/model-tiers.ts) models before Cheap ones. A key alone does not outrank a subscription: it may be there for a cheap or embedding model. Each leg shows its provider, model (`defaultChatModel`), tier when listed, and per-token or flat-rate billing; a Cheap tier orchestrator gets a warning. With more than one ready, a terminal run lists them and asks for a number (Enter keeps the first); `--yes`, `--dry-run` and a non-terminal print the others, and `--orchestrator <id>` picks one without asking ([setup-terminal-prompt.ts](setup-terminal-prompt.ts) reads both questions from one line reader). The worker is the first `llama-server` entry, served by the managed engine with its model on disk, or by an external server that answers. Otherwise it exits 1 with the next step: the `.env` variable or Manage › LLM › Cloud for a key, the Claude Code sign-in or install command, `models use <id>` for a model already on disk, or `models pull <id> --background` for the machine's balanced catalog pick.

It prints each change (`(unset) → value`), asks (a non-terminal needs `--yes`), and writes through [applyFusionSetupInConfig](../config/fusion-setup-commands.ts): one validated write of the new entry, `llm.activeTextProvider`, `llm.runMode.mode` and the fusion block. The legs are always pinned; the rest is filled only where unset, so a value you wrote is kept, and so is an enum value a newer build wrote ("kept (set by a newer version)"): `autoReplan: 1`, and on a priced orchestrator `escalation: "advisor"` and `turnBudgetUsd: 1` (the advisor's dollar cap needs a price; on a subscription leg only the counted caps hold a turn). A note explains the turn cap: once a turn's spend reaches it, no new delegation or worker starts and the orchestrator reports what is done; 0 means no cap. `config set` cannot address the fusion block, so `--budget <usd>` sets it (over a stored value too; `--budget 0` for none). `judge` and `isolation` (a global setting) stay off unless `--judge`/`--isolation` is passed; the output says so. A re-run that changes nothing prints "already set up" and exits 0. `--dry-run` writes nothing.

## Desktop state merge

`import atomic-desktop --source <dir> [--json]` merges the desktop app's former state dir (`~/.atomic-agent-desktop`) into the current one (`ATOMIC_AGENT_STATE_DIR`, default `~/.atomic-agent`) when the desktop moves onto the shared dir (ATO-416). The desktop runs it once and moves the plain files (config.json, .env, skills, traces, models) itself; this command handles only the databases:

- sessions and tasks keep their ids and are inserted only where the id is absent, so the target wins. A live turn arrives ended as interrupted, a running task arrives pending, and neither carries an owner mark.
- memory notes are added through `MemoryStore` unless the same text is already stored; profile facts through `ProfileStore` unless the target has any row for the key.
- lessons, procedures, votes, note links and embeddings are not copied; the embedding backfill or `memory reindex` rebuilds vectors.

Each source database is read from a private snapshot (a byte copy after a clean close, otherwise SQLite's online backup over a read-only connection), so the source is never written and nothing is deleted. Writes are short transactions that wait on the target's locks, so a TUI or `serve` may keep the target open. A re-run imports nothing new. `--json` prints one object, `{ok, sessions:{imported,skipped}, tasks, notes, profileFacts, warnings, error?}`; exit 0 only when every part imported. Implementation: [atomic-desktop importer](../import/atomic-desktop/atomic-desktop-importer.ts).

Checks: `npx vitest run src/cli` when tests are present; `npm run lint`; `npm run docs:check`.

## Handoff

`handoff --from claude-code|codex [--session latest|<id>] [--cwd <dir>] [--note <text>] [--list] [--json] [--no-open]` continues a Claude Code or Codex session that stopped mid-task (ATO-1154). It reads their transcript through the import readers ([handoff source](../import/handoff/handoff-source.ts)), saves it as a NEW native chat with a fresh `s-` id ([handoff session](../import/handoff/handoff-session.ts)), closes trailing tool calls that never got a result, and opens the TUI on it with `--session <id> --send <continuation message>`. `latest` is the newest session that ran in the current folder, else the newest anywhere. `--list --json` prints `{from, sourceDir, sessions:[{agent,id,mtimeMs,cwd,title,messageCount}]}`; `--json` without `--list` saves the chat without opening it and prints `{ok, sessionId, title, workingDir, from, sourceSessionId, turns, closedCalls, prompt}` (the desktop uses both).

Before saving, the carried history is fitted into a local model's window (ATO-1155, [fit-context](../import/handoff/fit-context.ts)): when it is larger than half the window (`--context <tokens>`, default the managed model's pinned `contextSize`, else 32768; `0` skips this), the head becomes an extractive checkpoint (`SessionCompaction`, `kind: "extractive"`, no model call) cut at a safe boundary, the newest records stay verbatim, and very long tool outputs in that tail are clipped in the middle. `--json` reports it under `context`.
